# Ф4 «Добор картинок»: отчёт

Пишется по ходу работы, не в конце (прогон долгий, сетевой, может оборваться).
Источник цифр — живые запросы к `data/forum.sqlite` и `data/assets/manifest.jsonl`
на момент старта фазы (2026-08-25 — 2026-08-26). Команды воспроизведения — рядом
с цифрами.

## 1. Расхождение «база 1763 / манифест 1484» — объяснено, обе системы правы

Коротко: **никакого реального расхождения нет**. Оба числа, по которым
сравнивали, посчитаны неверным способом — база построчно (с задвоением по
постам), манифест — по сырым строкам append-only лога (с задвоением по
истории). Если считать правильно — обе системы дают ОДНИ И ТЕ ЖЕ цифры.

### 1.1. База: строки таблицы vs уникальные URL

`attachments` — это таблица (mid, url, kind, status), одна строка на каждое
**упоминание** картинки в посте. Одна и та же картинка, процитированная в
нескольких темах, даёт несколько строк с одинаковым `url`. Задача добора —
скачать URL один раз, а не один раз на пост, поэтому считать нужно
`DISTINCT url`, а не строки.

```sql
-- строки (то, что дало "1763/6991/196/10")
SELECT status, COUNT(*) FROM attachments
WHERE kind IN ('external_image','local') GROUP BY status;
-- ok 1763, no_snapshot 6991, empty 196, failed 10

-- уникальные URL (то, что реально нужно считать)
SELECT status, COUNT(DISTINCT url) FROM attachments
WHERE kind IN ('external_image','local') GROUP BY status;
-- ok 1409, no_snapshot 5007, empty 174, failed 10  -- ровно цифры Ф2-отчёта
```

Проверено: у ВСЕХ 6600 уникальных URL статус одинаков во всех их строках
(`SELECT url, COUNT(DISTINCT status) ... HAVING COUNT(DISTINCT status) > 1` →
0 строк). То есть база внутренне непротиворечива, просто отчёт по ней надо
снимать через `DISTINCT url`, как и делал Ф2.

### 1.2. Манифест: append-only лог, а не таблица состояний

`assets_state.record()` **дописывает** строку в `manifest.jsonl` при каждом
событии, никогда не переписывая файл. На один URL за время добора приходится
до трёх строк:

1. `assets index` находит снимок в CDX → пишет `pending` (+таймстемп снимка);
2. `assets download` качает тело → дописывает финальный статус (`ok` /
   `empty` / `failed`);
3. `assets sieve --apply` (просев заглушек, Ruling 45) у части `ok` дописывает
   ещё одну строку `empty` поверх.

`assets_state.load()` — код, которым реально пользуется `sync_to_db` —
корректно берёт **последнюю** запись на URL (`out[rec["url"]] = rec`, простой
overwrite при проходе по файлу). Баг был не в коде конвейера, а в способе,
которым цифры сняли на этот раз: построчный `grep status | count` по файлу
без схлопывания по URL.

Проверка на живом файле:

```
wc -l data/assets/manifest.jsonl            → 8268 строк
distinct url                                 → 6600
URL с >1 записью                             → 1593
```

Разбор по паттерну переходов у этих 1593 URL:

| Переход | Число |
|---|---:|
| `pending → ok` | 1409 |
| `pending → empty` | 99 |
| `pending → ok → empty` (просев, Ruling 45) | 75 |
| `pending → failed` | 10 |
| **Итого** | **1593** |

То есть «1593 pending» из наивного счёта — это ровно первая (устаревшая)
строка лога для тех же самых URL, у которых вторая (и иногда третья) строка
уже несёт финальный статус. Если взять `assets_state.load()` (последняя
запись на URL) — манифест даёт **ok 1409, no_snapshot 5007, empty 174,
failed 10**, реального `pending` — **0**.

### 1.3. База и манифест — один и тот же набор URL, побайтово

```
manifest urls: 6600
db urls (kind filtered): 6600
in db not manifest: 0
in manifest not db: 0
```

Полное множественное равенство, не совпадение по количеству. **База и
манифест согласованы на 100 %** — то, что выглядело как «разные системы
дают разные числа», было одной и той же историей, прочитанной двумя разными
неверными способами (задвоение по постам с одной стороны, задвоение по
записям лога с другой).

### 1.4. Хосты — контрольная проверка

По ТЗ проверить хосты «1593 ожидающих»: наивный счёт по сырым строкам со
статусом `pending` даёт ровно `img-fotki.yandex.ru 281, i.piccy.info 146,
content.foto.mail.ru 108, forum.subaru-faq.ru 93, ...` — это те самые числа
из постановки. Финальный статус (по `load()`) этих же URL: **ok 1409, empty
174, failed 10, pending 0**. Совпадение хостов подтверждает: это не другой
источник данных, а те же самые 1593 URL, только увиденные через устаревшую
первую строку лога вместо актуальной последней.

## 2. Цифра Ф2 («возвращено 1409, 21,3 %») — верна, без поправок

Знаменатель Ф2-отчёта (`6600 = COUNT(DISTINCT url) FROM attachments WHERE
kind IN ('external_image','local')`) — это **весь** известный на сегодня
универсум адресов картинок/вложений форума, а не урезанная выборка. Доказано
в п. 1.3: манифест и база покрывают ровно эти же 6600 URL, ни одного лишнего
ни в одной из систем.

«1593 ожидающих», которые как будто выпали из знаменателя — на самом деле
**уже внутри** и 6600, и 1409/174/10/5007: это подмножество URL, для
которых нашёлся снимок в CDX, и по ним уже принято финальное решение (см.
п. 1.2, 1.4). Пропавшего хвоста нет.

**Вывод: пересчитывать нечего.** Цифра фазы Ф2 — **1409 / 6600 ≈ 21,3 %** —
верна и на момент отчёта, и сейчас; «нечестного знаменателя» не было, только
неверный способ прочитать append-only манифест при повторной проверке задним
числом.

## 3. Что такое «1593 ожидающих» — ответ

Это **не** адреса, которые проиндексировали и забыли скачать. Это URL, у
которых `assets index` нашёл снимок в CDX ещё в Ф2 (в противовес 5007, где
снимка не нашлось вовсе), и по которым `assets download` **в той же фазе**
довёл дело до конца: 1409 — реальная картинка, 174 — снимок отдался, но не
прошёл проверку содержимого (99 обычных пустышек + 75 заглушек хостингов,
просеянных отдельно), 10 — сетевой сбой при скачивании. У всех 1593 сегодня
стоит терминальный статус; фактически ожидающих (не тронутых со стороны
`download`) — **0**.

Единственная реальная сетевая работа, которая по конструкции конвейера ещё
не выполнялась — это то, что уже отмечено в `ф4-бэклог.md` пункт 4:
осознанный повторный запрос `no_snapshot` (5007 адресов, вдруг Wayback с тех
пор набрал новый снимок) и повторное скачивание `empty` (174 адреса, в
основном 99 настоящих пустышек — архив мог с тех пор отдать другой снимок).
Это и есть настоящий «добор», а не разбор 1593 «висящих» URL — по ним всё
уже решено.

## 5. Механизм добора для 268 картинок FAQ и блогов — построен

Порядок работ по решению координатора: сначала FAQ/блоги (маленький объём,
никогда не пробовали, механизма не было вовсе), потом `--retry no_snapshot`,
потом `--retry empty`.

### 5.1. Устройство

Новый модуль `pipeline/fetch_faqblog_assets.py` — по образцу
`fetch_assets.py`, собран из тех же кирпичей, а не написан с нуля:

- CDX-поиск, скачивание тела, пейсер (`fetcher.TokenBucketPacer`, тот же
  токен-бакет ~1,9 стр/мин), признак содержимого (`fetch_assets.
  _is_real_image`, включая просев заглушек `attachments.is_placeholder` —
  сторона ≤ 2 px и приговоры по хэшу `DECIDED_PLACEHOLDER_SHA256`), статусы
  и валидатор `--retry` (`fetch_assets.TERMINAL_STATUSES`/`RETRY_ON_DOWNLOAD`/
  `_retry_targets`) — переиспользуются напрямую импортом, не копируются;
- просев уже скачанного (`assets sieve`/`mark_empty`) — ДОСЛОВНО те же
  функции `fetch_assets.sieve_report`/`mark_empty`: они читают только
  манифест и диск, к таблице `attachments` не обращаются, поэтому позвать их
  с новым манифестом уже достаточно, копии не нужно;
- манифест — свой файл, `data/assets/manifest-faqblog.jsonl` (append-only,
  тот же формат и код `assets_state.record`/`load`, что у форума, но другой
  пул адресов — не путать историю двух доборов);
- каталог с файлами — ТОТ ЖЕ `data/assets/files/`, что у форумных картинок
  (Ruling Ф3 задача 2: один файл — одно имя от `attachments.asset_name`,
  один каталог на всё вики, без дублей).

**Пул адресов** — не весь `faq_images ∪ blog_images` (401 из 669 уже нашлись
в архиве Ф0/Ф1), а только то, чего `archive_assets.find` там не нашёл:
опрашивать Wayback про адрес, для которого файл уже лежит на диске без сети,
означало бы тратить вежливость впустую. Проверено тестом (`test_
fetch_faqblog_assets.py::test_pool_excludes_urls_already_covered_by_the_
archive`).

**Отражение в базе** — `fetch_faqblog_assets.sync_to_db`, тот же принцип, что
`archive_assets.sync_local_paths`/`assets_state.sync_to_db` («диск — истина,
база — отражение, отражение восстанавливается при каждой загрузке»): трогает
только строки `faq_images`/`blog_images`, у которых `local_path IS NULL`
ПОСЛЕ архивного шага — пулы не пересекаются по построению, SQL-фильтр
`WHERE local_path IS NULL` защищает от регрессии на случай ошибки порядка
вызова. Вызывается после `archive_assets.sync_local_paths` в трёх местах:
`ingest`/`all`, `faq load`, `blog load` (`pipeline/run.py`).

**Зеркало** (`mirror_faq._resolve_image`) — тот же принцип "одна функция на
базу и на вики", распространённый на второй источник: сперва архив (дешевле,
без сети), при промахе — манифест Wayback. `mirror_blog` использует ту же
функцию (как и раньше — она общая для обоих разделов).

Новый CLI: `python -m pipeline.run faqblog index|download|sieve`, флаги
`--faqblog-manifest` (свой) + общие `--assets-root`/`--limit`/`--retry`/
`--apply`, устройство один в один с `assets`.

### 5.2. Тесты

14 новых тестов (`tests/test_fetch_faqblog_assets.py` — 8, плюс 2 в
`tests/test_mirror_faq.py` про приоритет архива над Wayback-фолбэком и про
подстановку найденного через Wayback файла в заметку). Полный набор:
**642 зелёных** (было 632). Проверено явно: пул сборки адресов, роль
`--retry`, отказ от заглушки (1×1 GIF), нетронутость уже заполненных архивом
строк, обнуление `local_path` при пропавшем с диска файле, CLI-обвязка.

→ `faqblog sieve`) — раздел 5.4, после форумного добора по порядку
