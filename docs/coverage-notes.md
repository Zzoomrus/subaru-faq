# Отчёт покрытия архива: что в нём есть и чего нет

Источник: `pipeline/coverage.py` (`coverage.report`/`coverage.summary`/`coverage.to_csv`),
данные — `data/forum.sqlite` (собрана задачами 4–5), полный отчёт по всем темам —
`data/coverage.csv` (не в git, см. `.gitignore` — `data/` целиком вне репозитория).

Воспроизвести:

```bash
cd ~/code/Python/subaru-faq
.venv/bin/python -c "
from pathlib import Path
from pipeline import db, coverage
conn = db.connect(Path('data/forum.sqlite'))
rows = coverage.report(conn)
print(coverage.summary(rows))
coverage.to_csv(rows, Path('data/coverage.csv'))
"
```

## Почему пять групп, а не «ok/short/missing/extra» из брифа задачи 6

Бриф задачи 6 предполагал, что у каждой темы известно ожидаемое число ответов
(`replies_expected`), и предлагал формулу `COALESCE(replies_expected, 0) + 1`.
Проверка показала, что предположение неверно: у **1612 из 6338** тем в базе
`replies_expected IS NULL` — тема не встретилась ни в одном собранном
оглавлении раздела (`list_*.html`), а строка в `threads` создана фолбэком
`ingest.ensure_thread_from_page` со страницы самой темы (см. отчёт задачи 5).
Для таких тем «ожидание 1 пост» было бы не отсутствием данных, а прямой
ложью — рисовало бы для них ложное расхождение «постов больше, чем
ожидалось» на любом непустом content. Поэтому отчёт делит темы на **пять
непересекающихся групп**:

| Группа | Что значит | Кол-во | Доля от 6338 |
|---|---|---:|---:|
| `unverifiable` | `replies_expected IS NULL` — сверять не с чем | **1612** | 25.4% |
| `missing` | тема из оглавления, постов не сохранилось вовсе (`got == 0`) | **2829** | 44.6% |
| `ok` | тема из оглавления, число постов совпало с ожиданием | **1430** | 22.6% |
| `short` | тема из оглавления, постов меньше ожидаемого | **392** | 6.2% |
| `extra` | тема из оглавления, постов больше ожидаемого | **75** | 1.2% |

Сверка: `ok + short + extra` = 1430+392+75 = **1897** — это ровно множество
«тема есть и в оглавлении, и хотя бы один пост её» из отчёта задачи 5. Только
для этих 1897 тем проверка полноты вообще осмысленна. Итоговая сумма всех
пяти групп равна `threads` = 6338 без остатка — группы действительно
разбивают всё множество тем, а не только его часть.

## Группа `unverifiable` (1612 тем) — крауler не дошёл до нужной страницы листинга

Причина падения в базу, а не гипотеза: `ingest.ensure_thread_from_page`
создаёт строку `threads` для темы, у которой есть хотя бы одна страница с
постами (`read_*`/`message_*`), но которой нет ни в одном из 235 собранных
файлов `list_*.html`. Возможные механизмы (не разграничивал по каждой теме
отдельно — не требуется для отчёта, обе одинаково означают «сверить нечем»):
краулер Wayback не снял страницу листинга того раздела/страницы, на которой
эта тема упоминалась (глубокие/старые страницы листинга снимаются реже), либо
тема выпала из списка раздела к моменту снятия конкретного снимка листинга
(например, была перемещена/удалена и переиндексирована уже без неё). Для этой
группы `expected`/`diff` в CSV — пустые ячейки, а не `0` или `1`: у этих тем
почитать «сколько должно быть» неоткуда.

## Группа `missing` (2829 тем) — Wayback не сохранил ни одной страницы темы

Это ровно `threads_without_posts` из отчёта задачи 5. Важное уточнение
задания («1200+ тем Wayback не снял вовсе») — **устаревшая оценка из брифа
задачи 5**, которая предполагала, что множества «темы из оглавлений» (4726) и
«темы со страницами постов» (3509 после исключения антибот-страниц) почти
полностью пересекаются. Фактическое пересечение — только 1897, поэтому
реальное число тем без единого поста **2829**, а не ≈1200 (подробный разбор —
в отчёте задачи 5, раздел «Неожиданная находка»).

Проверил происхождение этой группы напрямую: у **2828 из 2829** тем в таблице
`pages` нет вообще ни одной строки — то есть у Wayback не нашлось ни одного
снятого `read_*`/`message_*`-файла для этих `tid`. Это дырка самого архива
(глубина краулинга Wayback ограничена), а не потеря на стороне парсера. У
**1 темы** (`tid=93386`, см. следующий раздел) страница снята, но не дала ни
одного поста — единственная тема, у которой `missing` вызвана содержимым
страницы, а не её отсутствием.

## Антибот-заглушки в `message_*` (10 файлов) — где они оказались в отчёте

Проверил утверждение задания, а не поверил ему на слово: открыл сырые файлы
с нулевым числом постов (`LC_ALL=C grep -o 'ctSetCookie\|ctMouseData' --binary-files=text`)
— во всех подтвердились маркеры антибот-челленджа (`ctSetCookie`/`ctMouseData`,
JS-код проверки браузера вместо `div.forum-post-text`). Это те же 10 файлов,
что подтверждены тестом `test_message_page_behind_bot_challenge_yields_no_posts`
(задача 4, фикстура `message_bot_challenge.html`) и посчитаны в отчёте задачи 5
как «8 уникальных тем без единого поста + 2 дубля контентных файлов»:

| `fid`/`tid` | Файл | Что в базе |
|---|---|---|
| 18/96388, 22/92460, 25/95763, 3/93533, 4/58261, 4/93532, 5/93523 | `message_*_0.html` | тема **не попала в `threads` вовсе** — нет ни в одном оглавлении, единственная страница дала 0 постов, фолбэк не срабатывает на пустой странице (см. `ingest.ensure_thread_from_page`, вызывается только когда `page.posts` не пуст) |
| 26/93386 | `message_26_93386_0.html` | тема есть в оглавлении (`replies_expected=0`) → группа **`missing`**, `expected=1`, `got=0` |
| 4/32503 | `message_4_32503_420176.html` | у темы есть другие, содержательные файлы (`message_4_32503_416882.html`, `_416897.html`, `_420168.html` — 12/15/16 постов соответственно) → тема в группе **`ok`** (16 из 16 постов сохранились через дубли) |
| 5/82516 | `message_5_82516_0.html` | аналогично, содержательный дубль `message_5_82516_415145.html` → группа **`ok`** (1 из 1) |

Итог: из 10 антибот-файлов **7 тем целиком невидимы в `coverage.csv`** — они
не попали в `threads` ни через оглавление, ни через фолбэк, потому что
единственная снятая страница не дала ни одного поста. Это слепая зона самого
отчёта: он считает только то, что физически осело в `threads`/`posts`, и не
может показать тему, для которой не выполнено ни одно из двух условий
попадания в базу. Явно фиксирую это как известное ограничение, а не молчу.

## Два файла с аномальными именами — пропущены как дубликаты, контент не потерян

`read_23_23771<br_1.html` (`<br` в сегменте TID) и
`message_7_68277_unread_mid.html` (текст вместо MID в последнем сегменте) не
матчатся регуляркой `_PAGE_RE` в `ingest.py` и пропускаются
(`stats["skipped_files"] == 2`). Задача 5 проверила побайтово: множество
`id="messageNNN"` в каждом из них совпадает 1:1 с корректно поименованным
файлом той же темы — контент не теряется, пропуск не создаёт дырки в отчёте.

## Группа `short` (392 темы) — проверка на две подпричины

Разбил 392 темы на «объяснимо» (не хватает целых страниц) и «не объяснимо
номерами страниц» — сравнил `threads.pages_expected` с числом различных
`page_no`, реально осевших в `pages` для этой темы:

| Подгруппа | Кол-во | Что значит |
|---|---:|---|
| Не хватает захваченных страниц (`captured_pages < pages_expected`) | **215** | Wayback не снял одну или несколько страниц темы целиком — самая понятная причина недостачи |
| Все ожидаемые страницы захвачены, но постов всё равно меньше | **177** | недостача внутри уже снятых страниц |

Для второй подгруппы (177 тем, «не объяснено номерами страниц») посмотрел
сырой HTML на конкретном примере — `tid=35857` (`read_2_35857_1.html`,
`pages_expected=1`, снята ровно 1 страница, `replies_expected=1` → ожидалось
2 поста): в самом файле физически присутствует только один
`id="messageNNN"` (`LC_ALL=C grep -o 'id="message[0-9]*"' --binary-files=text`)
— это не ошибка парсера (парсеру просто нечего разобрать сверх того, что
есть), а сам снимок Wayback этой страницы не содержит второго ответа. Скорее
всего дело во времени снятия снимков: страница листинга (со счётчиком
ответов) и страница темы снимались Wayback в разные моменты, и на момент
снятия страницы темы второй ответ либо ещё не был написан, либо страница
темы снята раньше страницы листинга. Ещё пример из этой подгруппы —
`tid=31601` (`fid=3`, «Замена двигателя...», 208 ожидается / 203 получено,
все 11 ожидаемых страниц захвачены) — при таком объёме (208 постов) вероятнее
недостача на уровне отдельных постов на многостраничной теме, а не целых
страниц. Итог: 177 тем из `short` — реальная, необъяснённая до конца дыра
архива (Wayback снял страницу, но не полный набор постов на ней), причину
для каждой по отдельности не устанавливал — это было бы за пределами
отчёта покрытия.

## Группа `extra` (75 тем) — временной разрыв между снимком оглавления и снимком темы

Проверил гипотезу «тема выросла между моментом, когда её посчитали в
оглавлении, и моментом, когда Wayback снял страницы её постов» — сравнил
`ts` (снимок Wayback) файла оглавления, давшего `replies_expected`, с `ts`
файлов темы из `manifest.jsonl`:

| `tid` | `expected`→`got` (`diff`) | `ts` оглавления | `ts` страниц темы (диапазон) |
|---|---|---|---|
| 37036 | 47→147 (+100) | 2013-02-03 | 2014-02-09 … 2014-04-11 (на ~1 год позже) |
| 34078 | 17→67 (+50) | 2012-11-23 | 2016-08-06 … 2016-08-08 (на ~4 года позже) |
| 41221 | 14→60 (+46) | 2014-07-24 | 2015-05-09 … 2015-05-10 (на ~10 месяцев позже) |

Во всех трёх случаях страницы темы снимались Wayback заметно позже снимка
оглавления — тема успела вырасти за время между двумя визитами краулера.
Гипотеза подтверждена конкретными датами, не осталась предположением.

Отдельная подгруппа `extra` — темы из списка «12 тем с расходящимся `fid`
между оглавлениями» (отчёт задачи 5): например `tid=34120`/`37300` имеют
`expected=1` при фактических 37–38 постах. У этих тем несколько
конкурирующих снимков оглавления (тема встречалась в листинге разных
разделов в разное время), и `ON CONFLICT DO UPDATE` оставляет только
последний по порядку обхода — если последняя по порядку версия листинга
случайно оказалась одним из самых ранних/малолюдных снимков темы, `expected`
получается заниженным. Не разбирал каждую из 12 отдельно — механизм тот же
(временной разрыв снимков), просто через призму дополнительного эффекта
last-write-wins при апсерте разноfid'овых оглавлений.

## Проверка на систематический перекос (по требованию задания) — перекоса нет

Прежде чем писать выводы, посмотрел распределение `diff` по всем 1897
проверяемым темам (`ok`/`short`/`extra`):

| `diff` | Кол-во | Доля |
|---|---:|---:|
| 0 | 1430 | **75.4%** |
| −1 | 78 | 4.1% |
| −2 | 40 | 2.1% |
| +1 | 29 | 1.5% |
| −5, −3 | 21 каждое | 1.1% каждое |
| остальные значения | ≤12 каждое | ≤0.6% каждое |

Мода распределения — **0** (75.4% тем сходятся точно), `diff = −1` — всего
4.1%, далёко не доминирует. Если бы формула «ответы + 1» была систематически
неверна для этого форума (например, форум на самом деле не считает
стартовый пост в `replies`, и правильная формула — `replies_expected` без
`+1`), мы увидели бы моду на `−1`, а не на `0`, и `ok`-долю в единицы
процентов. Этого нет — **вывод: формула из брифа (`replies_expected + 1`)
корректна**, найденные расхождения (`short`/`extra`) — это реальные дырки
архива (недостающие страницы/посты, временной разрыв снимков), а не
артефакт неправильной арифметики.

## Что осталось необъяснённым

- **177 тем из `short`** («все ожидаемые страницы захвачены, но постов всё
  равно меньше») — проверил механизм на 2 примерах (`35857`, `31601`), но не
  установил причину для каждой из 177 тем по отдельности: наиболее вероятная
  версия («снимок страницы темы снят раньше снимка листинга, ответ появился
  позже») правдоподобна, но не проверена индивидуально для всех 177.
- **7 из 10 антибот-тем** не видны в `coverage.csv` вовсе (см. раздел выше) —
  это ограничение самого отчёта (считает то, что попало в `threads`), а не
  дефект классификации. Итоговое число тем в архиве, вероятно, чуть больше
  6338, но точно оценить «сколько тем существует, но не оставило следа ни в
  оглавлении, ни в постах» по данным базы невозможно в принципе — это по
  определению не видно ей самой.
- **12 тем с конфликтующим `fid`** между оглавлениями — не проверял для
  каждой отдельно, что именно вызвало заниженный/адекватный `replies_expected`
  после `ON CONFLICT DO UPDATE`; для `34120`/`37300` в группе `extra` гипотеза
  «последний по обходу листинг оказался ранним снимком» правдоподобна, но не
  подтверждена по датам снимков листинга индивидуально (только по общей
  логике last-write-wins).
