## Находки (по убыванию серьёзности)

### 1. [ВЫСОКАЯ] Правило вхождения ответа пропускает минимум 2 настоящих дубля из-за пробелов

`faq_dedup.find_duplicates` сравнивает `(answer or "").strip()` как точную подстроку
`canon_body` без нормализации внутренних пробелов/переносов строк. Два движка сайта расставляют
переносы абзацев по-разному (тот же класс расхождения, что и `posts.text` vs `posts.markdown`,
уже задокументированный как системный в Global Constraint №1) — из-за этого текстуально
идентичные ответы не совпадают как `str in str`.

**Воспроизведение (боевая база `data/forum.sqlite`, только чтение):**

```python
import sqlite3, re
conn = sqlite3.connect("data/forum.sqlite")
a = conn.execute("SELECT answer_text FROM faq WHERE engine='old' AND nr=155").fetchone()[0]
b = conn.execute("SELECT answer_text FROM faq WHERE engine='bitrix' AND nr=140").fetchone()[0]
print(a.strip() in b)                                    # False — код это и находит, дубль не ставит
print(re.sub(r"\s+", " ", a).strip() in re.sub(r"\s+", " ", b).strip())  # True — тот же текст
```

Пары, найденные так (обе проверены глазами — текст действительно один и тот же):

- `FAQ старый 155` («Закисает автоматически выдвигаемая антенна, что делать?», 1766 знаков) —
  тот же рассказ автора об антенне, что `FAQ 140` («Закисшая автоматическая антенна»). Разница —
  одинарный `\n` у старого движка там, где у bitrix двойной `\n\n` между абзацами.
- `FAQ старый 114` («Какие параметры давления должны быть в автоматической коробке E-4AT?»,
  481 знак) — та же таблица давлений (кг/см²) и тот же следующий абзац, что `FAQ 168` («Давление
  в гидравлической системе коробки Е-4АТ»). Разница — табуляции у bitrix там, где у старого
  движка переносы строк.

Проверил боковые ложные срабатывания: то же ws-нормализованное сравнение по всем 174 записям
(с порогом длины 60 знаков) не даёт других новых пар сверх уже найденных 15 — только эти две.

**Последствие:** обе записи (`FAQ старый 114`, `FAQ старый 155`) в боевой вики **не помечены**
(проверено глазами — ни `дубль_чего` во фронтматтере, ни коллаута нет в файле
`wiki/Источники/FAQ/FAQ старый 155.md`). При написании статей эти два ответа получат
самостоятельные сноски наравне со своими каноническими двойниками `FAQ 140`/`FAQ 168` — то есть
одна мысль получит две сноски как два независимых свидетельства, ровно тот обман, против
которого была поставлена задача.

**Реальные числа:** дублей минимум **17** (15 найденных + 2 пропущенных), уникальных записей
**157**, а не 15/159, как записано в отчёте и в `docs/контракт-зеркала.md` §3 /
`docs/ф3-бэклог.md`. Утверждение отчёта «явно проверил все 5 [записей без совпадения по
вопросу] … 0 обоснован, не занижен по невнимательности» — фактически неверно: проверка была
точной посимвольной подстрокой без нормализации пробелов, и именно это дало ложный ноль.

**Фикс:** нормализовать пробелы (`re.sub(r"\s+", " ", s).strip()`) с обеих сторон перед
проверкой `in` в `find_duplicates`, пересчитать числа на боевых данных, обновить
`docs/контракт-зеркала.md` §3 и `docs/ф3-бэклог.md`, пересобрать зеркало (появятся 2 новых
файла с пометкой).

### 2. [СРЕДНЯЯ] Идемпотентность сброса в `apply()` ничем не защищена от регрессии

Бриф и отчёт явно называют сброс перед пересчётом ключевым свойством («Идемпотентно: сначала
всё сбрасывается в NULL»), но ни один тест не вызывает `apply()` вообще — тесты проверяют только
`find_duplicates` и рендер заметки с уже готовыми полями в БД.

**Воспроизведение мутацией** (в `git worktree`, не в общем дереве): убрал строку
`conn.execute("UPDATE faq SET duplicate_of_engine = NULL, duplicate_of_nr = NULL")` из
`apply()` — весь набор из 321 теста остаётся зелёным (`.venv/bin/python -m pytest -q` →
`321 passed`). Ручная проверка на копии базы (`/tmp/forum-copy.sqlite`) подтвердила, что
*сама* логика в коммите работает правильно (запись, которую я вручную пометила дублём
несуществующей канонической `bitrix/999999`, после `apply()` корректно сбрасывается в `NULL`,
т.к. правилам она больше не соответствует) — то есть баг не в поведении, а в отсутствии
regression-теста на него. Если это поведение случайно сломают позже, тесты не поймают.

**Фикс:** тест вида «предзаполнить `duplicate_of_*` мусорным значением у записи, которая по
текущим правилам НЕ дубль, вызвать `apply()`, проверить, что поле стало `NULL`».
