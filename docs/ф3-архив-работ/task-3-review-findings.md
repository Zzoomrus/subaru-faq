## 1. [ВЫСОКАЯ] `citable()` не узнаёт шапку поста, если в нике автора есть `*`

Регэксп шапки — `^\*[^*\n]+ · \d{2}\.\d{2}\.\d{4}[^*\n]*\*$`. Класс `[^*\n]+` запрещает
`*` в куске «до даты» — а форум цензурит часть ников звёздочками. На живом корпусе это
реально ломает распознавание на **6 постах в одной теме**:

```
wiki/Источники/Тема 24918.md:155:*Svetik**** Насонова · 10.01.2010 23:02:22 · #23*
wiki/Источники/Тема 24918.md:197:*Svetik**** **** · 16.01.2010 10:50:14 · #29*
wiki/Источники/Тема 24918.md:209:*Svetik**** **** · 17.01.2010 12:10:06 · #31*
wiki/Источники/Тема 24918.md:226:*Svetik**** **** · 20.01.2010 07:47:46 · #33*
... (всего 6, посты #23/#29/#31/#33/#35/#38)
```

`citable(notes.section(p, "Пост 205494"))` вернёт строку шапки **как есть** —
`*Svetik**** **** · 16.01.2010 10:50:14 · #29*` — это текст генератора (атрибуция), не
слова автора, а проверка дословности примет его как есть, потому что он лежит в теле
заметки буквально.

**Воспроизведение:**
```python
from pathlib import Path
from pipeline import notes
p = Path("wiki/Источники/Тема 24918.md")
s = notes.citable(notes.section(p, "Пост 205494"))
assert "Svetik" in s  # шапка не вычищена
```

Полная проверка на корпусе (все 48689 постов): у 48683 шапка распознаётся, у **6** — нет,
и все 6 — из-за `*` в нике:
```python
import re, glob
HEADING = re.compile(r"^##### Пост \d+$", re.M)
HEADER = re.compile(r"^\*[^*\n]+ · \d{2}\.\d{2}\.\d{4}[^*\n]*\*$", re.M)
for path in glob.glob("wiki/Источники/*.md"):
    text = open(path, encoding="utf-8").read()
    for m in HEADING.finditer(text):
        line = text[m.end():].split("\n")[2]
        if not HEADER.match(line):
            print(path, line)
```

Тест из брифа этого не поймал, потому что фикстура использует чистые имена (`Saka`,
`Anri`) — на брифовской строке паттерн работает, а брифовской строки с звёздочкой в нике
не было. Исполнитель тесты не расширял (буквально по брифу), поэтому и разрыв не всплыл.

**Правка:** заменить `[^*\n]+` на нежадный `.+?` (или на явный запрет только `\n`), раз
дата с `\d{2}\.\d{2}\.\d{4}` и так якорит правую границу.

## 5. [НИЗКАЯ, синтетика] `body()` не срезает вырожденный пустой frontmatter

```python
from pathlib import Path
from pipeline import notes
p = Path("/tmp/x.md")
p.write_text("---\n---\n\n# Title\nbody\n", encoding="utf-8")
notes.body(p)
# -> '---\n---\n\n# Title\nbody\n'  (frontmatter НЕ срезан!)
```

Причина: `text.find("\n---\n", 4)` ищет закрывающий разделитель начиная с позиции 4, а
у вырожденного (пустого) фронтматтера ведущий `\n` закрывающей строки стоит на позиции 3
— ровно перед точкой старта поиска, `find` его не видит, следующего совпадения нет,
`end == -1`, текст возвращается целиком.

На живом корпусе не проявляется (все 7040 заметок проверены — фронтматтер срезается
у каждой без остатка, все генераторы всегда пишут ≥1 поле), но это ровно тот класс
ошибки, о котором предупреждает бриф («разбор frontmatter по первому `---` уже давал
ложные результаты в прошлой фазе») — тест на этот случай в брифе тоже не было, потому
что фикстура всегда содержит поля.

Отдельный worktree (`/tmp/subaru-faq-review-notes3`, коммит `85414175`), удалён после
работы, дерево не тронуто. 337/337 зелёные — подтвердил сам.

**Механизм фикса.** Второй, теперь главный рубеж
(`test_every_generator_placeholder_constant_value_is_scrubbed_by_citable`) не читает
исходный текст модулей, а берёт `vars(module)` ПОСЛЕ импорта — то есть уже вычисленное
значение каждой заглавной строковой константы генератора — и гоняет его через `citable()`.
Старый AST-скан по исходнику оставлен первым рубежом (ловит объявленную, но нигде не
использованную константу).

**Проверка воспроизведения находки.** Повторил впрыск плейсхолдера в `mirror_blog.py`
всеми тремя формами по очереди (простой литерал / f-строка / конкатенация), без очистки
под него, прогон только `-k placeholder`, откат `cp` из сохранённой копии между попытками
(`diff` = 0 после каждого восстановления):
- литерал `LEAK_LITERAL = "(рецензия не сохранилась)"` — падают ОБА теста;
- f-строка `LEAK_FSTRING = f"(рецензия не сохранилась: {LEAK_ID})"` — старый AST-тест
  проходит МОЛЧА, новый падает;
- конкатенация `LEAK_CONCAT = "(рецензия" + " не сохранилась)"` — то же самое.

Совпадает с заявлением коммита буквально.

**Новая форма, которую не проверял ни я, ни исполнитель (по прямому запросу): плейсхолдер
литералом ПРЯМО ВНУТРИ функции генератора, без объявления константы.** Проверил две
разновидности:
- инлайн f-строка внутри функции (`out_probe = f"(рецензия потеряна: {post_id})"` внутри
  `_render_comments`, не присвоена никакому модульному имени) — **проходит МИМО ОБОИХ
  рубежей молча** (`5 passed` на `-k placeholder`, ни один тест не увидел утечку). Новый
  рубеж смотрит только `vars(module)` — локальная переменная внутри функции туда не
  попадает никогда, независимо от формы записи; старый AST-скан не матчит f-строку по той
  же причине, что и раньше (разбитые `ast.Constant`-куски).
- для контроля — инлайн ПРОСТОЙ литерал внутри той же функции (без f-строки, без
  константы) — тут старый AST-скан ловит (это всё ещё цельный `ast.Constant`, сканер не
  смотрит на то, присвоен ли он имени), падает `test_every_generator_placeholder_literal_
  is_scrubbed_by_citable`. Значит слепая зона — именно КОМБИНАЦИЯ «динамическая форма
  (f-строка/конкатенация) + не вынесено в константу», а не любой инлайн сам по себе.

Оба впрыска отменены между попытками, `diff` = 0, финальный прогон полного набора —
337/337.

**Итог по третьему ре-ревью.** Фикс верно чинит и воспроизводит находку прошлого раунда —
подтвердил сам, оба теста ведут себя ровно как заявлено. Но класс «плейсхолдер генератора»
всё ещё не замкнут полностью: инлайновый f-строчный/конкатенационный плейсхолдер внутри
функции, никогда не поднятый до именованной модульной константы, проходит мимо обоих
рубежей. Это **не блокер** для закрытия задачи 3 (два предыдущих раунда фиксов закрыли
всё, что было найдено на живом корпусе и что было явно попрошено проверить; этот случай —
синтетический, автор нового кода такую форму пока не написал) — но стоит явно
зафиксировать как известное ограничение контрактного теста для Ф4, когда генераторы
снова будут править: если правка добавит новый плейсхолдер именно инлайновой динамической
строкой без константы, контракт его не поймает.

### Вердикт по третьему ре-ревью

относятся к тому, что было найдено на живом корпусе, и обе стоит записать как известные
ограничения для будущих задач Ф3/Ф4, а не чинить сейчас точечными патчами.

## Четвёртое ре-ревью (коммит `50eab84e`, точечное — третий рубеж)

Отдельный worktree (`/tmp/subaru-faq-review-notes4`, коммит `50eab84e`), удалён после
работы, дерево не тронуто. 338/338 зелёные — подтвердил сам.

**Механизм.** `test_dynamic_placeholder_shaped_strings_must_be_module_constants` обходит
AST всех трёх генераторов, находит `JoinedStr` (f-строки) и `BinOp(Add)` (конкатенация)
ГДЕ УГОДНО в модуле, восстанавливает силуэт строки (`\0` на месте интерполяции) и падает,
если силуэт похож на плейсхолдер (`(...)`/`*(...)*`) и выражение не является прямой правой
частью присваивания заглавной модульной константе (те уже покрыты вторым рубежом).
Выражения, где силуэт не восстановить статически (внутри — вызов функции/переменная),
не флагуются вовсе.

### 1. Ложные срабатывания — нашёл реальное

Прогнал по всем трём генераторам как они есть — 0 существующих выражений флагуется
(`ast.walk` находит ровно 3 узла `BinOp(Add)` во всём коде трёх генераторов, все три —
`"\n".join(...) + "\n"`-подобные, у всех силуэт `None` из-за вызова функции внутри; `JoinedStr`
в коде сегодня нет вовсе) — подтверждено программно, не выборочно.

Придумал честную строку, которую тест зря отвергает — **получилось, это находка**:
диагностическое сообщение, вообще не имеющее отношения к телу заметки:

```python
def _debug_probe(tid_for_debug):
    """Честная диагностика, никогда не попадает в тело заметки."""
    print(f"(пропущено: {tid_for_debug})")
```

Добавил такую функцию в конец `mirror.py` (не трогая существующий код) — тест упал:
```
AssertionError: ... /pipeline/mirror.py:559 — силуэт '(пропущено: \x00)'
```
Причина: скан смотрит на ЛЮБОЙ `JoinedStr`/`BinOp(Add)` в модуле — независимо от того,
попадает ли он в `out`/тело заметки или это лог, диагностика, сообщение исключения,
CLI-вывод. Скобочная форма f-строки-статуса («(пропущено: …)», «(skipped: …)» — обычный
идиоматический вид лог-сообщения) достаточна для срабатывания. Это ровно тот раздражающий
случай, о котором вы предупреждали: тест упадёт на коде, который никак не угрожает
дословности цитат (никогда не попадает в `wiki/`), и первая реакция на такое — заглушить
тест, а не разбираться. Откатил добавление, `diff` = 0.

Квалифицирую это НЕ как блокер закрытия задачи: направление ошибки — в безопасную сторону
(ложный ОТКАЗ на честном коде, а не пропуск подделки, — противоположность риска, ради
которого весь этот механизм строился), и на сегодняшнем коде трёх генераторов срабатываний
нет. Но стоит явно записать как известное ограничение третьего рубежа: если Ф4 добавит в
эти три файла диагностику/лог/сообщение исключения такой скобочной формы — тест упадёт по
причине, не имеющей отношения к дословности цитат, и это нужно будет узнавать не по факту
раздражения, а по этой записи.

### 2. Слепая зона закрыта — подтверждаю

Повторил инлайн-пробу из прошлого раунда — `out.append(f"(рецензия потеряна: {post_id})")`
внутри `_render_comments`, не в константе — новый рубеж падает точно на этой строке, два
прежних молчат (`1 failed, 5 passed` на `-k placeholder`). Откатил, `diff` = 0.

### 3. Три рубежа не противоречат — подтверждаю

Впрыснул тот же плейсхолдер как f-строку, поднятую в модульную константу
(`LEAK_FSTRING_CONST = f"(рецензия не сохранилась: {LEAK_ID})"`) — упал ровно второй рубеж
(значение константы не вычищено), первый и третий молчат (третий верно не трогает то, что
уже покрыто вторым — id в `_module_level_constant_value_ids`). Единственный чёткий сигнал
«добавь паттерн очистки», без противоречия. Откатил, `diff` = 0.

### Вердикт по четвёртому ре-ревью
Слепая зона предыдущего раунда закрыта и подтверждена лично, три рубежа согласованы и не
дают противоречивых требований на одной подделке — оба пункта ОК. Нашёл один реальный
ложноположительный сценарий (диагностическая f-строка вида `(...)` где угодно в модуле,
не связанная с телом заметки) — это находка, не придирка, но не блокер: ошибка в безопасную
сторону, на сегодняшнем коде не проявляется. Рекомендация — зафиксировать как известное
ограничение (или сузить скан до выражений, попадающих в `out`/возвращаемое значение
рендер-функций, если будет время в Ф4), закрытие задачи 3 не задерживать.
