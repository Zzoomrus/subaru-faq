# Отчёт по задаче 6: отчёт покрытия

## Что сделано

Бриф задачи 6 писался в предположении, что у каждой темы известно ожидаемое
число ответов, и предлагал формулу `COALESCE(replies_expected, 0) + 1`.
Проверка базы показала, что предположение неверно: у 1612 из 6338 тем
`replies_expected IS NULL` (темы созданы фолбэком `ingest.ensure_thread_from_page`
со страницы, без строки в оглавлении — см. отчёт задачи 5). Формула из брифа
для них дала бы ложное «ожидался 1 пост» вместо честного «сверить нечем». По
явному указанию тимлида реализация отклоняется от кода в брифе: вместо
`{"ok","short","missing","extra"}` — пять непересекающихся групп
(`ok`/`short`/`extra`/`missing`/`unverifiable`), классификация вынесена в
`_classify()` с фиксированным приоритетом проверок (`unverifiable` → `missing`
→ знак `diff`).

1. `tests/test_coverage.py` — 4 теста: три сценария из адаптированного брифа
   (ok/short/missing/extra в одной фикстуре из 5 тем) + отдельный тест на тему
   с `replies_expected IS NULL`, где `got > 0` (проверяет приоритет
   классификации), + тест на наличие колонки `group` в CSV. Плюс тест-инвариант
   `test_null_expected_thread_with_zero_posts_is_unverifiable_not_missing`
   (NULL и 0 постов одновременно — на реальных данных не возникает, но код не
   должен путать эти два случая).
2. `pipeline/coverage.py` — `Row` (добавлено поле `group`, `expected`/`diff`
   типизированы как `int | None`), `report(conn)`, `summary(rows)` (ключи
   `threads/ok/short/extra/missing/unverifiable`), `to_csv(rows, path)`
   (добавлена колонка `group`).
3. Полный прогон по `data/forum.sqlite` → `data/coverage.csv` (6339 строк:
   заголовок + 6338 тем, не в git по `.gitignore` — `data/` целиком вне репо).
4. Проверка на систематический перекос формулы «ответы+1» — сделана до
   написания выводов, как требовал тимлид. Перекоса нет (ниже).
5. `docs/coverage-notes.md` — разбор каждой группы с цифрами, причинами и тем,
   что осталось необъяснённым.
6. Коммит `b5064ed`.

Границы брифа/тимлида соблюдены: парсеры и `ingest.py` не менялись, `sections`
не трогалась, зеркало не генерировалось. Субагенты не запускались.

## Проверка на систематический перекос — перекоса нет

Распределение `diff` по 1897 проверяемым темам (`ok`/`short`/`extra`):

| `diff` | Кол-во | Доля |
|---|---:|---:|
| 0 | 1430 | **75.4%** |
| −1 | 78 | 4.1% |
| −2 | 40 | 2.1% |
| +1 | 29 | 1.5% |
| −3, −5 | 21 каждое | 1.1% каждое |
| остальные | ≤12 каждое | ≤0.6% |

Мода — 0 (75.4%), `diff = −1` — только 4.1%, не доминирует. Если бы форум не
считал первый пост в `replies` (т.е. правильная формула была бы без `+1`),
распределение показало бы моду на −1 и мизерную долю `ok`. Этого нет.
**Вердикт: формула `replies_expected + 1` верна**, расхождения `short`/`extra`
— реальные дырки архива, а не ошибка арифметики.

## Разбор `short` (392 темы)

215 тем — не хватает целых страниц (`captured_pages < pages_expected`).
177 тем — все ожидаемые страницы захвачены, но постов внутри них всё равно
меньше. Проверил механизм на конкретном примере: `tid=35857`
(`read_2_35857_1.html`, `pages_expected=1`, снята 1 страница, ожидалось 2
поста) — в самом сыром HTML физически присутствует только один
`id="messageNNN"` (`LC_ALL=C grep -o 'id="message[0-9]*"' --binary-files=text`):
это не потеря парсера, снимок Wayback этой страницы сам не содержит второго
ответа. Второй пример — `tid=31601` (208 ожидается/203 получено, все 11
страниц захвачены) — недостача на уровне отдельных постов многостраничной
темы. Причина не установлена индивидуально для всех 177 — вероятнее всего,
разрыв во времени между снимком страницы темы и написанием более позднего
ответа.

## Разбор `extra` (75 тем) — временной разрыв снимков подтверждён по датам

Сравнил `ts` файла оглавления (дал `replies_expected`) с `ts` файлов страниц
темы из `manifest.jsonl`:

| `tid` | `expected`→`got` | `ts` оглавления | `ts` страниц темы |
|---|---|---|---|
| 37036 | 47→147 | 2013-02-03 | 2014-02-09…2014-04-11 |
| 34078 | 17→67 | 2012-11-23 | 2016-08-06…2016-08-08 |
| 41221 | 14→60 | 2014-07-24 | 2015-05-09…2015-05-10 |

Во всех трёх страницы темы снимались заметно позже оглавления — тема успела
вырасти. Гипотеза подтверждена датами, не осталась предположением. Отдельно
`tid=34120`/`37300` (из списка «12 тем с конфликтующим `fid`», задача 5) дают
`expected=1` при 37-38 постах — вероятно, тот же эффект через
`ON CONFLICT DO UPDATE` (последний по обходу листинг оказался ранним
снимком), по датам индивидуально не проверял.

## Судьба 10 антибот-файлов (`message_*` с `ctSetCookie`/`ctMouseData`)

Проверил утверждение задания эмпирически, не поверил на слово:
`LC_ALL=C grep -o 'ctSetCookie\|ctMouseData' --binary-files=text` на всех 10
файлах подтвердил маркеры антибот-челленджа (совпадает с тестом
`test_message_page_behind_bot_challenge_yields_no_posts`, задача 4).

| Судьба | Кол-во | tid |
|---|---:|---|
| Тема **не попала в `threads` вовсе** (невидима в отчёте) | 7 | 96388, 92460, 95763, 93533, 58261, 93532, 93523 |
| Тема в группе `missing` (есть в оглавлении, `expected=1`, `got=0`) | 1 | 93386 |
| Тема в группе `ok` (спасена дублирующим содержательным файлом) | 2 | 32503, 82516 |

**Важно:** 7 из 10 антибот-тем структурно не могут появиться в `coverage.csv`
— они не попали в `threads` ни через оглавление, ни через фолбэк (фолбэк
срабатывает только когда страница дала хотя бы 1 пост). Значит `threads=6338`
слегка недооценивает реальное число тем в архиве — часть тем существует
только как единственный антибот-снимок и не оставляет следа ни в одной
таблице. Зафиксировано в `docs/coverage-notes.md` как явное ограничение
самого отчёта.

## Коррекция устаревшей цифры из задания

Задание цитирует «1200+ тем Wayback не снял вовсе» — это устаревшая оценка
из брифа задачи 5, которая предполагала почти полное пересечение множеств

**2829**, не ≈1200. Разбор — в `docs/coverage-notes.md` и в отчёте задачи 5.

## Сомнения

1. **177 тем из `short`** («все ожидаемые страницы захвачены, но постов всё
   равно меньше») — механизм подтверждён только на 2 примерах (`35857`,
   `31601`), не проверял причину для каждой из 177 индивидуально.
2. **7 антибот-тем невидимы в отчёте целиком** — это ограничение самого
   отчёта (считает только то, что физически осело в `threads`), а не дефект
   классификации; сколько всего таких «слепых» тем в архиве (не только
   антибот-случай) — оценить по данным базы невозможно в принципе.
3. **12 тем с конфликтующим `fid`** между оглавлениями — не проверял для
   каждой отдельно даты снимков листинга; для `34120`/`37300` в `extra`
   гипотеза «last-write-wins подхватил ранний снимок» правдоподобна, но не
   подтверждена индивидуально по датам (только по общей логике конфликта).
4. Не проверял, встречаются ли антибот-маркеры (`ctSetCookie`/`ctMouseData`)
   и на `read_*`-страницах, а не только на `message_*` — задание и задача 5
   говорили только про `message_*`, за пределы этого не выходил.
