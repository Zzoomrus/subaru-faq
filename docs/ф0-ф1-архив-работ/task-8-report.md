## Добавление: фикс неидемпотентности `ingest_all` (по требованию тимлида)

Границы расширены тимлидом ещё раз — правка `pipeline/ingest.py` (код
задачи 5), последним делом фазы, чтобы следующая фаза (добор картинок и
статей, повторные прогоны загрузчика по той же базе) не наступила на ту
же мину, что и я в проверке воспроизводимости.

**Падающий тест написан первым**
(`tests/test_ingest.py::test_ingest_all_is_idempotent_on_rerun`) —
прогоняет `ingest_all` дважды на одном и том же `pages_dir`/`manifest` и
явно сверяет счётчики `threads`/`posts`/`pages`/`attachments` после
первого и второго прогона. Падение подтверждено явно: `attachments`
21 → 42 на фикстурах (было бы 29376 → 58752 на реальном корпусе).

**Решение**: использовать уже идемпотентную таблицу `pages` (`INSERT OR
REPLACE` по `key`) как признак «эта страница уже отдавала вложения в
attachments» — для уже виденных страниц цикл вставки `attachments` не
выполняется вовсе (`already_ingested` проверяется до апсерта `pages`,
чтобы отличить первый визит от повторного). `threads`/`posts`/`pages`
были идемпотентны и раньше (апсерты) — тест зафиксировал это явно, а не
подразумевал.

**Конфликта между двумя требованиями тимлида не возникло** (описать,
если найдётся — не нашёлся): «таблица отражает разметку» (намеренные
внутрипрогонные дубли `(mid, url)` сохраняются, схлопывание — дело
`pipeline.mirror`, не загрузчика) и «не терять статусы фазы добора» решаются
одним и тем же механизмом — уже виденная страница просто не трогается
повторным прогоном ни по количеству строк, ни по их содержимому.
Единственный неохваченный теоретический случай: если содержимое уже
обработанного файла страницы изменится на диске между прогонами (не
новый файл, а правка существующего) — вложения не переразберутся. Для
статического дампа Wayback это не ожидается, но стоит иметь в виду.

Дополнительные тесты:
- `test_ingest_all_still_ingests_newly_added_pages_after_rerun` — новые
  страницы, добавленные в `pages_dir` между прогонами, обрабатываются

## Что сделано

1. **`tests/test_check_mirror.py`** — падающий тест написан первым
   (`ImportError: cannot import name 'check_mirror'` — подтверждено явно
   до реализации). Три теста: битая ссылка + битый якорь (из брифа),
   чистое зеркало без находок (из брифа), плюс дополнительный —
   задвоенный якорь внутри одной заметки (третий счётчик из интерфейса
   `check_mirror.check`, брифом не покрыт синтетическим тестом отдельно).
2. **`pipeline/check_mirror.py`** — реализация ровно по брифу (регэкспы
   `LINK`/`ANCHOR`, три счётчика). 3/3 теста зелёные сразу после реализации.
3. **Найденный и исправленный дефект** (по требованию тимлида, задача
   расширена за границы брифа — правка `pipeline/mirror.py`, код задачи 7):
   первый прогон проверки на реальном зеркале дал `broken_links: 3` — не
   ложное срабатывание, а необработанный BBCode-мусор форума
   (`[[IMG]...`, `[[QUOTE]...`, `[[/URL [URL=...]]`, `[[url=...]`, 18
   постов в 13 темах), который Obsidian читает как открывающую скобку
   вики-ссылки. Падающий тест
   `tests/test_mirror.py::test_bbcode_leak_with_double_brackets_is_not_a_wikilink`
   написан первым, подтверждён падающим, затем `_escape_wikilink_open`
   в `pipeline/mirror.py` экранирует `[[` → `\[\[` в тексте поста
   (безусловно — `text` приходит из `html_text.plain_text`, которая уже
   снимает все наши markdown-ссылки/картинки, поэтому любые `[`/`]` в нём
   всегда буквальны). Собственные вставки `![[local_path]]` строятся из
   `attachments`, не из `text`, — экранирование их не касается.
4. **Полный прогон конвейера с чистого листа** (свежая `data/forum.sqlite`,
   явный вызов `ingest.ingest_sections` до `mirror.write_all` — амендмент
   тимлида №1 брифа) — числа ниже.
5. **Проверка воспроизводимости буквально**: временная копия каталога
   (`pipeline/` + сырые страницы архива, без `.git`/`.venv`), полный прогон
   с чистого листа в ней, побайтовое сравнение с рабочим каталогом.
6. **`docs/ф0-ф1-отчёт.md`** — итог всей фазы Ф0+Ф1 человеческим языком:
   цифры, покрытие, размер зеркала, оценка размера репозитория после
   добора картинок, найденный дефект, открытые вопросы.
7. По пути найден и **отдельно задокументирован, не исправлен** второй
   дефект: `ingest_all` не идемпотентен при повторном запуске на уже
   заполненной базе (`attachments` без дедупа/`ON CONFLICT` — простой
   `INSERT`, повторный прогон удваивает строки: 29376 → 58752 на эмпирике).
   Обнаружен ровно так, как боялся тимлид, когда просил проверить
   воспроизводимость: я по неосторожности прогнал полный конвейер второй
   раз на уже населённой рабочей базе (а не сразу во временной копии) —
   `data/forum.sqlite` в git не попадает (`.gitignore`), урона репозиторию
   не было, но рабочий файл пришлось пересобрать с нуля (`rm` +
   единый прогон), после чего числа совпали с ожидаемыми (6338/48689/…).
   Отдельно после этого сделана чистая проверка воспроизводимости во
   временной копии — уже без повторного прогона на одной и той же базе.

## Учтённые поправки тимлида к брифу

1. **`ingest.ingest_sections(...)` вызывается явно** перед
   `mirror.write_all(...)` во всех прогонах ниже — без него `sections`
   пуста и поле «раздел» в заметках пустое.
2. **Фронтматтер не резался по первому вхождению `--- ` как подстроки.**
   Я не парсил фронтматтер в `check_mirror.py` вовсе (проверка работает
   по regex на `[[...]]`/`^p\d+`, без выделения границ фронтматтера), так
   что ловушка с `---` внутри заголовков (`Тема 18928.md` и другие — `---`
   встречается и в заголовках, и в самом тексте постов, проверил `grep`)
   не могла сработать. Явно проверил: в имеющемся `tests/test_mirror.py`
   хелпер `_frontmatter` уже режет по `"\n---"` (закрывающая строка), а не
   по первому вхождению подстроки — ловушка учтена задачей 7, не
   потребовалось трогать здесь.
3. **Проверка целостности доказана на пустом наборе межзаметочных ссылок.**
   Реальный корпус зеркала действительно не содержит межзаметочных ссылок
   вовсе (появятся в следующей фазе) — три синтетических теста в
   `tests/test_check_mirror.py` подтверждают, что `check()` ловит битую
   ссылку, битый якорь и задвоенный якорь независимо от реальных данных.
