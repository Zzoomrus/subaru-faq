## Отклонения от брифа

Бриф давал селекторы «на глаз» по нескольким страницам; полный прогон по всем 235 оглавлениям выявил, что часть из них не соответствует реальной разметке или ловит мусор. Все отклонения закреплены докстрингом в `pipeline/parse_listing.py`.

1. **`div.forum-item-title` → `span.forum-item-title`.** В брифе — `div`, в реальной разметке (проверено на всех 235 файлах, `grep -c 'div class="forum-item-title"'` = 0, `grep -c 'span class="forum-item-title"'` > 0 везде) — всегда `span`. С брифовым селектором парсер вернул бы 0 строк.

2. **Автор темы.** Брифовый селектор `span.forum-item-author span:last-of-type` брал текст **"автор:"**, а не имя — потому что имя автора не обёрнуто в отдельный `<span>`, это текстовый узел-сосед: `<span class="forum-item-author"><span>автор:</span>&nbsp;Vladimir</span>`. Исправлено: берём полный текст `span.forum-item-author` и регуляркой отрезаем префикс `автор:\s*`.

3. **Число страниц — скоуп на `span.forum-item-pages`, а не на `str(row)` целиком** (брифовый код брал весь `str(row)`). На части страниц (`list_12_1.html` и, видимо, шире — см. п.4) в один `<tr>` вложены соседние строки; скан всей строки на `PAGEN_1=` подхватывал номера страниц **чужой** темы.

4. **Системная битая разметка таблицы (найдено на полном прогоне, не было в брифе вовсе).** На `list_12_1.html`: не хватает закрывающего `</tr>`, из-за чего и `lxml`, и встроенный `html.parser` вкладывают ~35 соседних строк ВНУТРЬ одного `<tr>`-контейнера. `select_one` внутри такого контейнера находит *первое* совпадение, а не «своё»: `TID=15537` (реально `replies=8397/views=2838025/pages=420`) получал из контейнера чужие `replies=2669/views=1155788` от `TID=27731` — при этом `pages` для той же строки извлекались верно. Поломка непредсказуема по полям и не чинится точечно — контейнеры (строки со вложенными `<tr>`) целиком отбрасываются (`_is_leaf_row`); настоящие данные для каждой темы всегда присутствуют отдельной корректно изолированной листовой строкой. Проверка (`row.find("tr") is None`) применена как фильтр перед разбором строки.
   Закреплено тестом `test_malformed_container_row_is_skipped_not_misparsed` на фикстуре `tests/fixtures/list_12_1.html` — без фикса тест падает (`420 == 134` → AssertionError), проверено вручную откатом фикса.

### Сверка «~3522» из брифа задачи 5

`task-5-brief.md` ожидает после загрузки в БД `threads ≈ 3522 и больше`. Разобрался, откуда это число и почему у меня 4726:

- Уникальных `tid` среди файлов **с архивированным содержимым темы** (`read_*`/`message_*` в `data/raw/archive/pages/`): `ls | grep -E '^(read|message)_' | sed ... | sort -nu | wc -l` → **3518** — это практически то самое «~3522» из брифа (расхождение на 4 темы, видимо, округление/более раннее измерение).
- Значит: **3518 тем имеют хотя бы одну архивную страницу с постами**, а ещё **4726 − 3518 = 1208 тем (≈26%) присутствуют только в оглавлениях** (есть строка с заголовком/автором/счётчиками), но ни одной `read_`/`message_`-страницы для них в архиве не сохранилось.
- Это не баг парсера оглавлений — просто у краулера архива не всё было заскраплено. Важно для задачи 6 (проверка покрытия): ~1200 тем закономерно окажутся «просмотров/тема есть, постов 0» не из-за ошибки парсинга, а из-за реальной дыры в архиве. Стоит завести это отдельной группой в `docs/coverage-notes.md`, а не путать с настоящими пропусками.

### Побочное наблюдение (не чинил, не тестировал целенаправленно)

Битая разметка (п. 4 выше) не уникальна для `list_12_1.html` — беглая проверка показала, что строки-контейнеры со вложенными `<tr>` встречаются **во всех 235 файлах** (всего 416 таких контейнеров на корпус, при этом только 235 из них совпадали с реальной ссылкой на тему и раньше давали по одной паразитной строке — отсюда точное совпадение "5150 → 4915 = ровно 235"). Похоже, шаблон форума сам генерирует эту незакрытую `</tr>` в конце определённого блока на каждой странице листинга. `_is_leaf_row` отбрасывает такие строки универсально, независимо от файла, так что это не требует отдельного фикса — упомянуто для контекста, если кто-то будет удивляться происхождению цифры 235.

## Сомнения / что стоит учесть в следующих задачах

1. **`ThreadMeta.fid` — из `href`, не из имени файла.** В 13 строках это расходится с разделом, где тема физически показана в листинге. Для задачи 5/6/7 (группировка по разделам, генерация зеркала по разделам) стоит явно решить, какой `fid` считать «истинным» — сейчас парсер отдаёт то, что велит интерфейс (только `html`, без доступа к имени файла).
2. **12 тем с противоречивым `fid` между файлами** (тема физически «переезжала» между разделами) — при `ON CONFLICT(tid) DO UPDATE SET fid=excluded.fid` в брифе задачи 5 результат зависит от порядка обработки файлов (`sorted(glob)` — лексикографический, не хронологический). Возможно, для этих 12 тем стоит зафиксировать финальный `fid` вручную/эвристикой, а не полагаться на порядок сортировки файлов.
3. **~1208 тем без архивных страниц** (см. сверку с 3522 выше) — не относится к задаче 3, но задаче 6 нужно знать про эту группу заранее, иначе расхождения покрытия будут выглядеть как масштабный баг, а не как ожидаемая дыра архива.
4. Ничего сверх задачи 3 не делал: страницы тем (`parse_thread`), загрузка в БД, зеркало — не трогал.
