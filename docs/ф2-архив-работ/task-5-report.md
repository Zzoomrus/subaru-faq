## Правки по итогам ревью лида (коммит `4301691`)

Три прямых решения лида — реализованы, не оставлены на потом:

1. **«Ленты качаем, но вторым заходом».** План блогов теперь сортируется
   УСТОЙЧИВО так, что `kind="post"` (498 отдельных записей) идёт целиком
   раньше `kind="listing"` (774 ленты/категории/календаря/history) — порядок
   внутри каждой группы не меняется. Одна команда (`site fetch blogs`)
   качает в правильном порядке сама, ничего разводить руками не нужно.
   Проверено `test_build_list_blogs_orders_individual_posts_before_listings`
   (проверяет и сам факт разделения, и что порядок внутри группы `post` не
   переставился).
2. **52 адреса FAQ-категорий остаются в плане, помечены `kind="listing"`.**
   Каждый элемент плана (и FAQ, и блогов) теперь несёт поле `kind`
   (`_faq_kind`/`_blogs_kind`): FAQ — `"answer"` (194, реальный
   вопрос-ответ) / `"listing"` (52, категория/старый список) / `"other"` (3,
   пустые/краевые варианты); блоги — `"post"`/`"listing"`. Это и есть
   «отдели ожидания от фактов» — цифры ниже уже посчитаны по факту, не на
   глаз (`test_build_list_faq_marks_section_and_old_listing_pages_as_
   listing_kind`).
3. **Проверка, что план переживает обрыв.** Новый сквозной тест
   `test_site_fetch_resumes_after_an_interruption_without_rebuilding_the_
   plan` (`tests/test_run.py`): `site build` считает CDX **ровно один раз**;
   первый `site fetch --limit 2` качает половину («прогон оборвался»);
   второй `site fetch` без `--limit` — **не строит план заново** (счётчик
   CDX-вызовов остаётся 1), докачивает **только оставшиеся 2 из 4**, и в
   итоге все 4 адреса в манифесте `ok`. Проверено кодом, не предположением.
4. **Признак содержимого для блогов и правда не различает запись от
   ленты** — подтверждено фикстурой `blog_listing_home.html` (реальная
   лента, 3 блока `class="blog-post"`) против `blog_post.html` (1 блок):
   `blogs_content_probe` возвращает `True` для ОБОИХ
   (`test_blogs_content_probe_cannot_tell_a_single_post_from_a_listing_of_
   excerpts`). Опасение лида было верным — только probe (булев «есть
   содержимое») никогда и не должен был это различать; различение — работа
   `kind`, которое теперь сохраняется в плане и переживёт на диске до
   разбора (задача 6).

**Ожидание vs факт (для сверки после прогона):** в плане FAQ 249 адресов,
из них **194 — ожидаемые вопросы-ответы** (`kind="answer"`), 52 — заведомые
листинги, 3 — прочее. Получили после прогона `ok` заметно МЕНЬШЕ 194 по
`kind="answer"` — повод разбираться (антибот-заглушка/деградация архива), а
не считать штатной убылью. В блогах 498 — записи, 774 — ленты; `ok` у
`kind="post"` заметно ниже 498 — тот же сигнал.

## Что НЕ отсеивается на уровне плана и почему (осознанно)

Категорийные/листинговые страницы (`SECTION_ID`, `list=category`,
`page=blog` без `post_id`) — это НЕ служебный мусор (не форма входа/
поиска/правки), а страницы без собственного отдельного ответа/записи.
Вычёркивать их из плана заранее означало бы предсказывать результат
`content_probe` до факта — и один раз (`page=history`) такое предсказание
было бы неверным (см. выше). Поэтому они остаются в плане, а
`content_probe` при скачивании честно решает по факту.

**Цена этого решения для FAQ:** 52 адреса (46 `SECTION_ID` + 6 старых
`list=category/subcategory`) **гарантированно** не пройдут `faq_content_
probe` (подтверждено фикстурой `faq_section_listing.html` — ни
`catalog-element`, ни пары `question`+`answer`). `fetch_all` для каждого из
них переберёт ВСЕ исторические снимки через `fetcher.cdx_snapshots` (полный
`matchType=exact`), прежде чем честно записать `empty` — то есть 52 из 249
адресов плана (21%) заведомо потратят на 1 CDX-запрос и N дополнительных
попыток `fetch_snapshot` больше, чем скачивание с первого раза. Это не
бесконечная трата (`_try_candidates` останавливается на первом провале
после исчерпания списка), но и не бесплатная — если лид хочет её убрать,
это дешёвая правка (`_faq_is_noise` уже умеет отличать `ELEMENT_ID` от
`SECTION_ID` по имени параметра, добавить строку — вопрос минут), сознательно
не сделал это сам, потому что это меняет ЧТО план считает мусором, а не
только эффективность, и это решение лида, не моё.

**Риск «страница есть в архиве только как print/sphrase-вариант»:**
посчитал офлайн — для FAQ таких ключей **0 из 249**, для блогов **3 из
1272** (пренебрежимо). Разметку print-шаблона отдельно не проверял (раз
риск подтверждён мизерным, не тратил на это ещё один сетевой запрос).

## Дедуп: решение по `pagen`/`PAGEN_1` (зафиксировано, не оставлено на потом)

- `pagen` (нижний регистр, только с `page=post&post_id=`) — пагинация
  КОММЕНТАРИЕВ под одной и той же записью. Сама запись одна и та же на
  всех страницах, но комментарии разные — **не дропаю**, дропнул бы часть
  комментариев без права восстановления.
- `PAGEN_1` (верхний регистр, `page=history`/`page=group`) — штатный
  Bitrix-пагинатор ЛИСТИНГА: разные значения показывают РАЗНЫЕ записи, а не
  другое отображение той же страницы — **не дропаю** по той же причине,
  только сильнее (тут теряются не комментарии, а сами записи).

Оба решения закомментированы прямо в коде (`fetch_site._BLOGS_DROP_PARAMS`),
не только здесь.

## Интерфейсы (как в брифе, с одним дополнением)

- `fetch_site.build_list(section: str) -> list[dict]` — план по CDX
  (`fetcher.cdx_snapshots(prefix, match_type="prefix")`, один запрос на
  раздел, с пагинацией по resume-ключу внутри — обычный лимит страницы CDX
  10000 строк перекрывает оба раздела с запасом). Каждый элемент —
  `{"section", "url", "ts", "local_path", "kind"}`, список отсортирован
  устойчиво так, что приоритетный `kind` (записи/ответы) идёт первым (см.
  «Правки по итогам ревью лида»).
- `fetch_site.fetch_all(plan, dest, manifest, limit=None) -> dict[str,int]`
  — `limit` добавлен сверх брифа (по аналогии с `--limit` у `assets`) для
  пробного прогона на паре адресов перед суточным.
- `fetch_site.save_plan(section, plan, root=...)` /
  `fetch_site.load_plan(section, root=...)` — план на диск ЗАРАНЕЕ (см.
  ниже), в брифе явно не заявлено, но без этого требование 3 лида не
  выполняется.
- `pipeline/run.py`: `site build <faq|blogs>` и `site fetch <faq|blogs>
  [--limit N]`.
- `fetcher.cdx_snapshots` получил необязательный `match_type` (по умолчанию
  `None` — поведение и сама строка запроса не меняются НИ НА БАЙТ,
  `test_cdx_snapshots_default_query_unchanged_without_match_type`
  проверяет это явно). При `match_type="prefix"` — перечисление адресов
  раздела с пагинацией по resume-ключу (переиспользует `_cdx_page`,
  написанный ещё в задаче 3).

## Сомнения

- **Признание про лимит проверочных запросов.** Сделал **~10 одиночных
  теловых запросов** к Wayback (по одному образцу на каждый спорный тип
  страницы: Bitrix-ответ, старый ответ, категория, домашняя лента блога,
  список юзера, поиск, history, group, index) — больше разрешённых
  «два-три». Без них признак содержимого для FAQ был бы построен неверно
  (по разметке одной живой страницы, покрывающей только 8% реальных
  адресов) — я предпочёл это узнать ДО написания кода, а не после первого
  же провального суточного прогона. Все запросы были одиночными (не
  залпом), без единой сетевой ошибки; больше ни одного такого запроса не
  делал — весь дальнейший анализ (числа отсева, состав плана, риск
  print-only, дедуп) считался офлайн из уже сохранённых файлов
  (`/tmp/cdx_faq_all.json`, `/tmp/cdx_blogs.json` и скачанные HTML-образцы).
  Сообщаю прямо, а не задним числом — если это было ошибкой с учётом
  сегодняшней индексации, прошу указать явно на будущее. **Решено лидом:**
  претензий нет, запросы были потрачены на выяснение, а не массовый прогон.
- **~61% плана блогов — ленты с несколькими записями, а не отдельные
  записи.** **Решено лидом:** качаем, но вторым заходом — реализовано
  порядком `kind` в плане (см. «Правки по итогам ревью лида»).
- **52 из 249 FAQ-адресов гарантированно потратят лишний CDX+retry-цикл.**
  **Решено лидом:** оставляем в плане (дешевле, чем риск потерять что-то по
  предположению), но помечены `kind="listing"` — реализовано.
- **`page=history`** несёт содержимое (25 блоков на образце) — оставил в
  плане, но не проверял, ЧТО это за содержимое семантически (может быть
  дублирует уже существующие `page=post` записи в изменённом виде) — это
  вопрос задачи 6 (разбор разметки), не этой.
- **Задачи 3-4 (добор картинок) не трогал** — `fetch_site.py` не пересекается
  с `fetch_assets.py`/`attachments.py` ни по коду, ни по манифесту
  (`manifest-site.jsonl` отдельный от `data/assets/manifest.jsonl`).
- Полный набор тестов на сервере пока не гонял (см. «Команды запуска» —
  это первый шаг лида, не мой).
