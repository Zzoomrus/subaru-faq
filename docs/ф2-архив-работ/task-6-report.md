## Дефект: дублирующие «Вопрос:»/«Ответ:» в разделе «Ответ»

### Причина

Раздел FAQ мигрировал со старого движка на Bitrix, и у части записей всё
тело `catalog-element` перенеслось ЦЕЛИКОМ — вместе со служебными метками
«Вопрос:»/«Ответ:», которые в старом движке были отдельными ячейками
таблицы, а в Bitrix стали просто текстом внутри одного HTML-поля. Заголовок
`h1#pagetitle` при этом остался НАЗВАНИЕМ ТЕМЫ (как в хлебных крошках), а
не вопросом — потому что Bitrix изначально не проектировался вокруг «один
вопрос = один заголовок».

### Три формы дефекта (проверено на полном корпусе — 177 скачанных страниц)

Всего дубли нашлись у **70 из 154** записей Bitrix (у старого движка — у
**0 из 23**: там `question` и так берётся из отдельной ячейки, дублировать
ей неоткуда). Формы:

| форма | сколько | что делали |
|---|---|---|
| только метка «Ответ:», без вопроса | 34 | заголовок уже верен, снять метку |
| «Вопрос:‹текст›Ответ:‹текст›» | 34 | сравнить текст с заголовком (см. ниже) |
| «Вопрос:» без парной «Ответ:» | 2 | граница неоднозначна, см. «Сомнения» |

Из 34 записей формы 2 у **32** текст вопроса из тела РАСХОДИТСЯ с
заголовком (заголовок — название темы), у 2 совпадает буква в букву
(FAQ 112, FAQ 113).

### Решение по вопросу vs заголовку

**Настоящий вопрос важнее названия темы** (ориентир лида, подтверждён
данными: у 32 из 34 записей заголовок — это именно название темы каталога,
а не переформулировка вопроса). Название темы не выбрасывается — уходит во
второй алиас, чтобы поиск/ссылки по старому названию продолжали находить
заметку. Реализация:

- `FaqEntry` получил поле `title: str | None` — заполняется ТОЛЬКО когда
  вопрос из тела найден и отличается от заголовка h1 (сравнение без
  учёта регистра/пунктуации — `_loosely_equal`).
- `faq.title` (новая колонка, nullable) — `NULL` у старого движка всегда, и
  у Bitrix там, где дублирования не было или заголовок совпал с вопросом.
- `mirror_faq.render_entry`: `## Вопрос` показывает `question` (тело, когда
  есть; иначе заголовок как раньше); `aliases` — `[question]` либо
  `[question, title]`, если `title` заполнен.

Реализация в `parse_faq._split_embedded_qa` (три регэкспа под три формы
выше); граница «вопрос / ответ» — литеральная метка «Ответ:», а не пустая
строка: часть страниц разделяет вопрос и метку ответа ОДНИМ переводом
строки (FAQ 76), часть — через `<br>`, что рендерится в markdown как ПУСТАЯ
строка (FAQ 141) — если резать по первой пустой строке, вопрос с блочным
переносом обрывался бы на середине. Метка «Ответ:» — надёжный якорь в обоих
стилях.

### 4. Утечка HTML-комментариев в markdown — измерено и починено

Причина: `bs4.Comment` — ПОДКЛАСС `NavigableString`, а `html_text._render`
проверял только `isinstance(node, NavigableString)` — без явного
исключения текст `<!-- ... -->` рендерился как обычный текст. Подтверждено
изолированно: `html_text.to_markdown('<p>a<!-- SPCode -->b</p>')` →
`'a SPCode b'`.

**Замер масштаба по всему корпусу** (SQL по свежепересобранной базе):

| раздел | всего записей | несут утечку |
|---|---|---|
| FAQ (`faq.answer_md LIKE '%SPCode%'`) | 174 | **23** (13%) |
| посты форума (`posts.markdown LIKE '%SPCode%'`) | 60982 | **0** |

Проверил и шире, не только по слову «SPCode» — `grep` по сырым страницам
подтвердил, что ВСЕ HTML-комментарии с непустым текстом на корпусе FAQ —
это варианты одного маркера старого WYSIWYG-редактора (`SPCode Start`/
`SPCode End`/`SPCode u2 Start/End`/`SPCode auto-link start/end`, 24 сырых
файла из 177). На форуме комментарии с текстом тоже есть (`HotLog`,
`Yandex.Metrika`, баннеры) — но ВСЕ в шаблоне страницы (шапка/подвал), а
не внутри `div.forum-post-text`, который единственно попадает в парсер —
поэтому 0 из 60982 постов задеты фактически.

**Решение: чиню сразу**, а не откладываю. 23 из 174 (13%) — это не
«единицы», это заметная, систематическая (не случайный шум одной страницы)
доля видимого мусора в базе знаний. Ключевой довод не в счётчике, а в
природе правки: пропуск HTML-комментария при рендере в текст —
безусловно корректное поведение (комментарий НИКОГДА не должен быть
видимым текстом, ни в браузере, ни в любом другом рендерере), а не
эвристика с риском ложного срабатывания. Правка на уровне общего
рендерера `_render` — три строки, покрыта тестом
(`test_html_comments_do_not_leak_into_markdown`), 226/226 тестов зелёные
после неё.

**Проверка эффекта на реальных данных:** пере-прогон `all --rebuild`
изменил ровно **24 заметки — и все 24 в `wiki/Источники/FAQ/`** (23
записи `faq` + пересчёт схлопнутых дублей), **0 заметок форума** — числом
подтверждает то, что показал SQL-замер: утечка была специфична для
раздела FAQ. Пример (`FAQ 223`, до/после):

```diff
- SPCode u2 End
+
  (на примере Форестера, но относится ко всем)
```
