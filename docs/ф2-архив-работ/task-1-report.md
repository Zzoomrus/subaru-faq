## Сомнения (по значимости)

### 1. `db_error`: сузил проверку с `"DB query error"` до `<b>DB query error.</b>`

Бриф дал `if b"DB query error" in data: return "db_error"`. На корпусе (5938
файлов) это даёт **не 1, а 3 совпадения**:

```bash
cd ~/code/Python/subaru-faq && LC_ALL=C grep -l --binary-files=text "DB query error" data/raw/archive/pages/*.html data/raw/archive/broken/*.html
```
```
data/raw/archive/pages/read_2_31752_1.html
data/raw/archive/pages/read_2_43243_1.html
data/raw/archive/broken/read_18_41771_1.html
```

Первые два — настоящие посты форума, где пользователи **цитируют** увиденную
ими на сайте ошибку простым текстом (`...DB query error.<br />Please try
later....` внутри `div.forum-post-text`) — это контент, не пустышка. Настоящая
страница ошибки оборачивает фразу в `<b>DB query error.</b>` (проверил байт-в-
байт в `data/raw/archive/broken/read_18_41771_1.html`). Я сузил проверку до
`b"<b>DB query error.</b>" in data` — дословный тест из брифа проходит без
изменений (в нём фраза уже дана с этой разметкой), а корпусная проверка даёт
ровно 1/1 без ложных срабатываний:

```bash
cd ~/code/Python/subaru-faq && LC_ALL=C grep -l --binary-files=text '<b>DB query error.</b>' data/raw/archive/pages/*.html data/raw/archive/broken/*.html
```
```
data/raw/archive/broken/read_18_41771_1.html
```

Это единственное место, где я отступил от дословного текста реализации из
брифа — не от интерфейса и не от дословных тестов, только от одной строки
внутри функции, и с полным эмпирическим обоснованием. Если лид хочет
буквально `"DB query error"` без тегов — одна строка правки, тест из брифа
всё равно пройдёт (в нём тоже есть `<b>`, так что оба варианта дают
`"db_error"` на дословном тесте; разница проявляется только на двух реальных
цитатах в корпусе).

### 3. `cdx_snapshots`: `limit=50` в брифе может отсекать САМЫЕ свежие снимки для сильно заархивированных адресов ⚠️

Проверил живьём (см. выше метод, без модуля — сырой CDX-запрос), чем CDX
сортирует ответ **по умолчанию**, до нашего `sorted(rows, reverse=True)`:

```bash
curl -s "https://web.archive.org/cdx/search/cdx?url=subaru-faq.ru&output=json&fl=timestamp,original&filter=statuscode:200&limit=5"
```

Результат — 5 самых **старых** снимков (2001-2002 год), не самых свежих:

```
[["timestamp","original"],
["20011209062407","http://www.subaru-faq.ru:80/"],
["20020126001711","http://www.subaru-faq.ru:80/"],
["20020401181042","http://www.subaru-faq.ru:80/"],
["20020402103241","http://www.subaru-faq.ru:80/"],
["20020530011056","http://www.subaru-faq.ru:80/"]]
```

То есть CDX по умолчанию отдаёт снимки **от старых к новым**, а
`limit=N` (положительный) берёт первые N — то есть N **самых старых**, а не
случайные/свежие. Код брифа делает `_get(...limit=50...)`, затем
`sorted(rows, reverse=True)` — это сортирует по убыванию **только те 50
записей, что уже пришли**, а раз это старейшие 50 из всех снимков URL, то
результат — «самые свежие среди самых старых 50», а не самые свежие снимки
вообще. Для адреса с >50 снимками (например, `subaru-faq.ru/` — вероятно,
их сотни) реально свежие снимки в выборку **никогда не попадут**.

Это прямо противоречит глобальному ограничению фазы («Перебирать все снимки
от свежего к старому, а не доверять первому») и общей логике отката к более
старым снимкам, на которую я ссылаюсь в пункте 2 (откат работает, только
если свежие снимки вообще есть в списке).

Живьём проверить исправление (`limit=-50` — по документации CDX
отрицательный limit берёт последние N, то есть самые свежие) в моменте не
удалось: во время проверки `web.archive.org/cdx` отдавал `503 Temporarily
Offline` (плановый/внеплановый даунтайм архива, не связан с этим кодом) —
переподтвердить нужно отдельно, когда сервис восстановится. Не менял
код по своей инициативе, значение `limit=50` дано в брифе дословно —
но по факту это, похоже, баг: для тем/страниц с небольшим числом снимков
(типичный форумный тред) он не проявляется (все снимки помещаются в 50), а
для часто архивируемых адресов (корень сайта, популярные листинги,
возможно топовые FAQ) — проявится. Рекомендую перед прогоном на сервере
(задачи 2/3/5) заменить `limit=50` на `limit=-50` (или убрать лимит вовсе)
и перепроверить сортировку живым запросом, когда архив снова доступен.

`antibot` из `looks_empty` вовсе как самостоятельный признак (не (a)+(b), как
я рекомендовал, а именно вырезать байтовый признак из модуля скачивания).
Реализовано дословно по ТЗ лида, без отклонений.

Коммит: `1bb6174` — "fix(fetcher): признак содержимого передаёт вызывающий,
убрать байтовый antibot-маркер" (`pipeline/fetcher.py`, `tests/test_fetcher.py`).

### Что сделано

1. **TDD.** Сначала дописал 10 падающих тестов на новое поведение (запуск
   `tests/test_fetcher.py -v` до правки кода — 10 failed / 13 passed, включая
   `TypeError: looks_empty() got an unexpected keyword argument 'content_probe'`
   и `AttributeError: ... no attribute 'looks_empty_binary'`), потом реализовал.
   Главный тест задания —
   `test_looks_empty_page_with_antibot_marker_and_real_content_is_not_empty`:
   страница с маркерами `ctSetCookie`/`ctMouseData` **и** настоящим текстом
   поста (`div.forum-post-text`) не считается пустой ни без `content_probe`,
   ни с ним.
2. **`looks_empty(data, content_probe=None)`.** Оставил только то, что верно
   всегда: `<b>DB query error.</b>` (сужение из пункта 1 «Сомнения» не
   трогал — оно уже было принято) и общий порог размера (1024 байта, только
   для HTML). Байтовый `antibot`-признак убран целиком — вердикта `"antibot"`
   в возвращаемых значениях больше не существует. Если передан
   `content_probe` (`bytes -> bool`, «есть ли содержимое») и он говорит
   «нет» — `"no_content"`. Порядок проверок: `db_error` → `content_probe` →
   размер — `db_error` идёт первым как безусловная сигнатура, размер
   последним, чтобы `content_probe=True` на маленькой странице всё равно
   ловился как `too_small` (проверено тестом
   `test_looks_empty_content_probe_true_still_enforces_size_threshold`).
3. **Порог для двоичных данных — отдельная функция `looks_empty_binary(data,
   content_probe=None)`.** Решил в пользу отдельной функции, а не параметра
   у `looks_empty`, по трём причинам: (а) семантика байтового порога для
   HTML и бинарных данных не просто разная по значению, а разная по
   применимости — для HTML это осмысленный универсальный сигнал, для
   бинарных данных объекта проверки «мало байт» не существует вообще
   (валидный PNG/JPEG весит меньше 1024 байт), то есть это не «другое число
   в том же слоте», а отсутствующий слой проверки; городить это одним
   параметром (`min_bytes=None` → отключить) means двусмысленный флаг
   «выключить проверку по умолчанию включённую», это менее читаемо на месте
   вызова, чем два отдельных имени функций; (б) `looks_empty_binary` не
   содержит проверки `db_error` — она HTML-специфична (ищет тег `<b>` в
   разметке страницы ошибки БД), для бинарных данных бессмысленна и её
   отсутствие подчёркивает разными именами функций, а не веткой `if
   binary:` внутри одной; (в) вызывающий код (задача 2 — картинки) и так
   пишется отдельно от HTML-скачивания, поэтому явно другое имя функции не
   добавляет накладных расходов на месте использования. `looks_empty_binary`
   без `content_probe` может утверждать только полное отсутствие данных
   (`None` → `"too_small"`, сохранил как есть для совместимости с
   поведением `looks_empty` на этом крайнем случае); с `content_probe` —
   `"no_content"`, если проверка (например, попытка декодировать байты как
   изображение) говорит «невалидно».
4. **Корпусная проверка (5938 файлов, воспроизводимо).**

   Без `content_probe`, весь корпус (`data/raw/archive/pages` +
   `data/raw/archive/broken`):

   **Ровно 1 `db_error`, 0 ложных.** Ветки `antibot` в выводе больше нет

   С `content_probe = lambda d: b"forum-post-text" in d`, на файлах
   **строго из `data/raw/archive/pages/`** (без `broken/` — там всего 1
   файл, `read_18_41771_1.html`, и он db_error, до probe не доходит) по
   маскам `message_*.html` + `read_*.html` (5701 файл — это все страницы
   отдельной темы/сообщения в корпусе `pages/`; `list_*`/`index_*` внутри

## Правка 2: `cdx_snapshots` брал 50 самых старых снимков вместо свежих (limit)

Ревью нашло дефект ровно тот, что был описан в пункте 3 «Сомнения» выше и
намеренно не был исправлен без санкции (значение `limit=50` было дано в
брифе дословно). Лид дал явную санкцию: дословное значение из брифа против
явно сформулированного глобального ограничения фазы («перебирать все
снимки от свежего к старому, а не доверять первому») — побеждает
ограничение.

Коммит: `d32a49a` — "fix(fetcher): cdx_snapshots — брать последние 50
снимков, а не первые (limit отрицательный)".

### Что сделано

1. **Падающий тест.** `test_cdx_snapshots_requests_freshest_snapshots_not_oldest`
   мокает `urllib.request.urlopen`, перехватывает фактический `req.full_url`
   и парсит query-параметры — проверяет, что уходит `limit=-50`, а не `50`.
   До правки: `AssertionError: assert ['50'] == ['-50']`. Существующий тест
   на сортировку (`test_cdx_snapshots_skips_header_and_sorts_fresh_first`,
   свежие первыми на смокированных данных) не трогал — он и раньше был
   корректен, баг был не в сортировке уже полученных строк, а в том, какие
   строки CDX присылает по умолчанию при позитивном `limit`.
2. **Фикс: `limit: "-50"`, не безлимит.** CDX по умолчанию отдаёт снимки от
   старых к новым; положительный `limit=N` берёт первые N записей потока —
   то есть N САМЫХ СТАРЫХ, а наша `sorted(rows, reverse=True)` после этого
   сортирует только уже полученные (старые) 50 записей. Отрицательный
   `limit=-N` у CDX означает "последние N" — то, что нужно. Выбрал
   отрицательный лимит, а не снятие лимита вовсе, по двум причинам: (а) без
   лимита ответ для сильно заархивированных адресов (корень сайта — по
   живой проверке ниже что-то около 50+ снимков только за 2022-2026,
   вероятно многие сотни за всю историю) непредсказуемо растёт, а токен-
   бакет всё равно ограничивает нас ~2 стр/мин — построить список из тысяч
   кандидатов, из которых реально понадобятся первые несколько, только
   удлиняет и время ответа CDX, и риск таймаута; (б) 50 кандидатов на откат
   уже сильно превышает практический бюджет отката (retries по факту
   единицы, не десятки) — если ни один из 50 свежайших снимков не даёт
   контента, следующие 50 более старых с точки зрения "неудачного периода
   сайта" вряд ли ведут себя иначе. Отрицательный лимит с тем же числом 50
   — минимальное исправление направления при сохранении масштаба, заданного
   брифом.
3. **Докстринг `cdx_snapshots` дополнен** объяснением бага и почему нужен
   именно отрицательный, а не нулевой лимит — задачи 2-8 читают код, не
   только этот отчёт.
4. **Живая проверка свежести (сеть).**

   Сырой запрос (без модуля, для независимой проверки формата CDX):
   ```bash
   curl -s -m 30 "https://web.archive.org/cdx/search/cdx?url=subaru-faq.ru&output=json&fl=timestamp,original&filter=statuscode:200&limit=-5"
   ```
   ```

   ["20260418164511","http://subaru-faq.ru/"],
   ```

  правка этой задачи.
